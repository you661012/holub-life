# ADR 001 — Rule 객체를 Resident에 전달하는 방식

- 날짜: 2026-11-11
- 상태: **결정 1, 결정 2 확정, 구현 완료** (2026-11-11)
- 관련 코드: `Resident.java`, `Cell.java`, `Neighborhood.java`, `Universe.java`, `Rule.java`, `ConwayRule.java`, `HighLifeRule.java`

## 1. 문제

생존 규칙을 `Rule` 인터페이스와 구현체(`ConwayRule`, `HighLifeRule`)로 분리했다. `Resident.figureNextState()`의 판정을 다음과 같이 `Rule`에 위임하려 한다.

```java
// 변경 전
willBeAlive = (neighbors==3 || (amAlive && neighbors==2));
// 변경 후
willBeAlive = rule.nextState(amAlive, neighbors);
```

이렇게 바꾸자 `rule`이 선언되어 있지 않다는 컴파일 오류가 났다. `Resident` 안에 `rule`이라는 변수도, 그 변수가 가리킬 객체도 없기 때문이다.

가장 단순한 해결은 `Resident`에 필드를 두는 것이다.

```java
private Rule rule = new ConwayRule();
```

이 상태로 기존 `ResidentTest` 9개는 수정 없이 통과했다. 그러나 `Resident` 인스턴스는 4,096개이고(`Neighborhood(8, Neighborhood(8, Resident))`), 인스턴스마다 `ConwayRule` 객체를 따로 갖게 된다. 사용자가 실행 중에 메뉴에서 규칙을 바꾸면 4,096개가 모두 새 규칙을 따라야 하는데, 이 구조에서는 한꺼번에 바꿀 방법이 없다.

**결정할 것: 실행 중 규칙 교체가 가능하도록, `Resident`가 사용할 `Rule`을 어디에 두고 어떻게 전달할 것인가.**

## 2. 검토한 대안

| | 방식 | `Cell` 인터페이스 |
|---|---|---|
| A | 규칙 보관 객체(`RuleHolder`)를 Singleton으로 두고 `Resident`가 접근 | 변경 없음 |
| B | `RuleHolder`의 참조를 `Resident`가 생성자로 전달받아 필드에 보관 | 변경 없음 |
| C | `figureNextState()`의 매개변수로 `Rule`을 전달 | **변경** |
| D | `Cell`에 `setRule()`을 추가하고 Composite 구조를 따라 위임 | **변경** |

네 대안은 두 번의 갈림길로 나뉜다.

```
결정 1: 규칙에 관한 것을 Cell 인터페이스에 드러낼 것인가?
├─ 드러낸다              → C, D
└─ Resident만 규칙을 안다 → 결정 2: Resident가 RuleHolder를 어떻게 얻는가?
                              ├─ A: Singleton 접근
                              └─ B: 생성자로 전달
```

### C. 메서드 매개변수

```java
boolean figureNextState(Rule rule, Cell north, Cell south, ...);
```

- 구현: `Universe`가 매 세대 `outermostCell.figureNextState(rule, ...)`를 호출하고, `Neighborhood`가 받은 `rule`을 `grid`의 각 원소에게 그대로 넘긴다. `Resident`는 규칙을 보관하지 않고 받은 것을 바로 사용한다.
- 장점: 전역 상태가 없다. 이웃 8개를 매개변수로 넘기는 기존 방식(Flyweight)과 같은 생각이다.
- 단점: `Cell` 인터페이스가 바뀌어 `Resident`, `Neighborhood`, `Cell.DUMMY`, `Universe`를 모두 수정해야 한다. 기존 `ResidentTest` 9개가 `figureNextState()`를 이웃 8개로 호출하고 있어 테스트도 전부 고쳐야 한다.

### D. `setRule()`을 Composite 구조로 위임

```java
// Cell
void setRule(Rule rule);

// Neighborhood
public void setRule(Rule rule) {
    for (int row = 0; row < gridSize; ++row)
        for (int column = 0; column < gridSize; ++column)
            grid[row][column].setRule(rule);
}

// Resident
public void setRule(Rule rule) { this.rule = rule; }

// Cell.DUMMY
public void setRule(Rule rule) { }
```

- 구현: 규칙이 바뀔 때 `Universe`가 `outermostCell.setRule(rule)`을 한 번 호출한다. 기존 `clear()`, `transition()`과 같은 경로로 4,096개의 `Resident`까지 전달되고, 각 `Resident`가 자기 필드에 저장한다.
- 장점: `Universe`는 호출 한 번으로 끝나고 구조를 몰라도 된다. 기존 Composite 위임과 일관된다.
- 단점: 규칙을 사용하지 않는 `Neighborhood`와 `Cell.DUMMY`가 규칙 전달 메서드를 구현해야 한다. `Cell` 인터페이스가 더 커진다.

### A. Singleton `RuleHolder`

```java
willBeAlive = RuleHolder.instance().current().nextState(amAlive, neighbors);
```

- 구현: 현재 규칙을 보관하는 `RuleHolder`를 프로그램에 하나만 두고, `Resident`가 판정할 때마다 접근한다. 규칙 교체는 `RuleHolder.instance().change(rule)`.
- 장점: `Resident`의 수정이 한 줄이다. `Universe.instance()`, `Clock.instance()` 등 기존 코드의 방식과 같다.
- 단점: `Resident`가 `RuleHolder`에 의존한다는 것이 메서드 본문을 읽어야 드러난다. 전역 상태라 한 테스트에서 바꾼 규칙이 다른 테스트에 영향을 줄 수 있다.

### B. 생성자로 `RuleHolder` 전달

```java
private final RuleHolder holder;
public Resident(RuleHolder holder) { this.holder = holder; }
public Cell create() { return new Resident(holder); }
...
willBeAlive = holder.current().nextState(amAlive, neighbors);
```

- 구현: `Universe`가 `RuleHolder`를 하나 생성해 프로토타입 `Resident`에 넘긴다. `Neighborhood`가 `prototype.create()`로 복제할 때 같은 참조가 전달되어 4,096개가 같은 `RuleHolder`를 가리킨다. 규칙 교체는 `holder.change(rule)`.
- 장점: `Resident`가 무엇에 의존하는지 생성자에 드러난다. 테스트마다 별도의 `RuleHolder`를 넘길 수 있다. 매개변수 없는 생성자를 남겨 기본값을 Conway로 하면 기존 `ResidentTest` 9개를 고치지 않아도 된다.
- 단점: `Resident`의 필드, 생성자, `create()`와 `Universe`의 생성 부분을 수정해야 한다. `create()`에서 참조를 넘기는 것을 빠뜨리면 일부 `Resident`만 다른 `RuleHolder`를 갖게 된다.

### A, B 공통: `RuleHolder`를 거치는 이유

`Resident`가 `Rule`을 직접 필드로 가지면 규칙을 바꿀 때 4,096개의 필드를 모두 바꿔야 한다. `Resident`가 `Rule`이 아니라 `Rule`을 보관하는 객체 하나를 함께 참조하면, 그 객체의 내용만 바꿔도 모든 `Resident`가 다음 판정부터 새 규칙을 사용한다.

```
Resident × 4,096 ──▶ RuleHolder(1개) ──▶ ConwayRule 또는 HighLifeRule
```

## 3. 결정 1 — `Resident`만 규칙을 알게 한다 (C, D 제외)

**선택: 규칙에 관한 것을 `Cell` 인터페이스에 드러내지 않는다.**

이유:

- 위에서 아래로 전달하는 방식(C, D)은 규칙을 사용하지 않는 `Neighborhood`와 `Cell.DUMMY`까지 규칙 관련 코드를 갖게 된다. 규칙으로 생사를 판정하는 것은 `Resident`뿐이다.
- 기존 `Cell` 인터페이스에는 이미 같은 종류의 문제가 있다. `edge()`와 `widthInCells()`는 `Neighborhood`에만 의미가 있는데 인터페이스에 있어서 `Resident`가 형식적으로 구현한다(`widthInCells()`는 1을 반환). `createMemento()`는 `Resident`에서 호출하면 실행 중에 `UnsupportedOperationException`을 던진다. 같은 문제를 하나 더 만들지 않기로 했다.
- C는 기존 테스트 9개를 모두 고쳐야 한다. 구조를 바꾼 뒤에도 기존 테스트가 그대로 통과하는 것을 보이려는 목적과 맞지 않는다.

수업 자료와의 관계 (13 Composite, "Where to place Child Mgt. Interface?"):

- 슬라이드는 자식 관리 메서드를 `Component`에 두면 **Transparency**(Leaf와 Composite를 똑같이 다룸), `Composite`에만 두면 **Safety**(잘못된 호출이 컴파일 단계에서 걸림)를 얻는다고 설명한다.
- Holub의 `Cell`은 Transparency를 택한 설계다. 그 대가가 위의 `edge()`, `widthInCells()`, `createMemento()`이다.
- 이번 문제는 방향이 반대다. `setRule()`은 Composite가 아니라 **Leaf(`Resident`)에만** 의미가 있다. 이를 `Cell`(Component)에 두는 D는 Transparency를 유지하는 선택이고, `Resident`에만 두는 것은 Safety에 가까운 선택이다.
- `Resident`에만 두면 `Universe`가 `Cell` 타입의 `outermostCell`을 통해 규칙을 전달할 수 없다(Transparency를 잃는다). 그래서 메서드 호출로 내려보내는 대신 공유 객체(`RuleHolder`)의 내용을 바꾸는 방식을 쓴다.

포기한 것:

- D의 장점인 "`Universe`가 `outermostCell.setRule()` 한 번으로 끝낸다"와 기존 설계 방식과의 일관성.

## 4. 결정 2 — `RuleHolder`를 Singleton으로 만들지 않고 생성자로 전달한다 (B)

**선택: B.**

A와 B는 `Resident`가 `RuleHolder`에게 현재 규칙을 물어 `Rule` 객체를 얻는다는 점이 같다. 차이는 `RuleHolder`가 Singleton인가 아닌가 하나다. Singleton이 아니면 어디서나 꺼낼 수 있는 `instance()`가 없으므로 생성자로 전달받아야 한다.

이유:

- `Rule` 객체(`ConwayRule`, `HighLifeRule`)는 필드가 없어 변하지 않는다. 반면 `RuleHolder`는 "현재 규칙"을 필드로 갖고 `change()`로 바뀐다. 변하는 값을 가진 객체가 프로그램에 하나뿐이면 누군가 바꾼 값을 모두가 보게 된다.
- 테스트 실행(`./gradlew test`) 한 번은 프로그램 실행 한 번이고, 그 안에서 테스트 메서드들이 차례로 호출된다. A에서는 모든 테스트 메서드가 같은 `RuleHolder` 하나를 보게 되어, 한 테스트가 규칙을 바꾸면 그 값이 다음 테스트에 남는다. 예: `RuleHolderTest`가 HighLife로 바꾼 뒤 `ResidentTest`의 `죽은_셀은_이웃이_6개여도_살아나지_않는다`가 실행되면 실패한다.
- B에서는 테스트마다 `new RuleHolder()`로 자기 것을 만들 수 있어 어떤 규칙으로 검사할지를 테스트별로 정할 수 있다. 프로그램을 실행할 때는 `Universe`가 하나만 만들어 프로토타입 `Resident`에 넘기므로 4,096개가 같은 것을 본다.
- Singleton은 인스턴스가 정확히 하나여야 할 때 쓰는 패턴이다(수업 자료 9 Singleton: "Exactly one instance of a class is required"). `RuleHolder`에 필요한 것은 유일함이 아니라 `Resident`들이 같은 객체를 공유하는 것이고, 공유는 같은 참조를 전달하는 것으로 충분하다.
- 기존 생성 구조와 맞는다. `Neighborhood`는 `prototype.create()`로 `Resident`를 복제하므로, 프로토타입에 `RuleHolder`를 넣어 두면 복제본이 같은 참조를 물려받는다(수업 자료 20 Prototype의 shallow cloning과 같은 모양).

확인한 것: A 방식과 B 방식으로 같은 검사 두 개(① 규칙을 HighLife로 변경, ② 죽은 세포는 이웃 6개여도 살아나지 않음)를 차례로 실행해 보았다. A에서는 ②가 실패했고 B에서는 통과했다. (저장소 밖의 실험 코드로 확인. 프로젝트 테스트로는 아직 재현하지 않음.)

포기한 것:

- A는 `Resident`의 수정이 한 줄이다. B는 `Resident`의 필드, 생성자, `create()`와 `Universe`의 생성 부분을 고쳐야 한다.
- 기존 코드의 `Universe.instance()`, `Clock.instance()`와 같은 방식을 쓰는 일관성.
- `create()`에서 참조 전달을 빠뜨리면 `Resident`마다 다른 `RuleHolder`를 갖게 된다. → "`create()`로 만든 `Resident`는 같은 `RuleHolder`를 공유한다"는 테스트로 막는다.

구현할 때 지킬 것:

- 매개변수 없는 `Resident()` 생성자를 남기고 기본값을 Conway로 한다. 기존 `ResidentTest` 9개를 수정하지 않기 위해서다.
- `RuleHolder`의 필드는 `volatile`로 선언한다. 세대 진행은 `Clock`의 타이머 스레드에서, 규칙 변경은 메뉴를 처리하는 스레드에서 일어나기 때문이다.

## 5. 결정에 이른 과정

1. 61줄을 `rule.nextState(...)`로 바꾸고 컴파일 오류를 확인했다.
2. 필드 `private Rule rule = new ConwayRule();`로 해결하고 `ResidentTest` 9개가 통과하는 것을 확인했다.
3. 이 구조로는 실행 중에 4,096개의 규칙을 바꿀 수 없다는 문제를 확인했다.
4. "상위 수준에서 적용해야 하지 않나"라는 생각에서 D(위에서 아래로 위임)를 떠올렸다.
5. 수업 자료의 Transparency 대 Safety 슬라이드가 같은 종류의 문제임을 확인하고, 문제를 "규칙에 관한 것을 `Cell`에 둘 것인가, `Resident`에만 둘 것인가"로 정리했다.
6. 위에서 아래로 내리면 규칙을 쓰지 않는 클래스들이 규칙 관련 코드를 갖게 된다는 점 때문에 `Resident`에만 두기로 했다.
7. `Resident`만 규칙을 알게 하려면 4,096개가 규칙 보관 객체(`RuleHolder`) 하나를 함께 참조해야 함을 확인했다.
8. A와 B의 차이가 `RuleHolder`가 Singleton인가 아닌가 하나임을 정리했다.
9. Singleton이면 테스트 실행 한 번 안에서 모든 테스트가 같은 규칙 상태를 보게 되고, 아니면 테스트마다 정할 수 있다는 점 때문에 B를 선택했다.

## 6. 구현 결과 (2026-11-11)

결정대로 구현했다.

| 클래스 | 변경 |
|---|---|
| `Rule` (신규) | 인터페이스. `boolean nextState(boolean alive, int neighbors)` |
| `ConwayRule`, `HighLifeRule` (신규) | `Rule` 구현체. 필드 없음 |
| `RuleHolder` (신규) | 현재 `Rule`을 `volatile` 필드로 보관. `current()`, `change(Rule)`. Singleton 아님 |
| `Resident` | `Rule`을 직접 갖지 않고 `RuleHolder` 참조를 필드로 가짐. 생성자 2개(매개변수 없음 → 새 `RuleHolder`, `RuleHolder` 전달). 판정은 `holder.current().nextState(amAlive, neighbors)`. `create()`는 `new Resident(holder)` |
| `Universe` | `RuleHolder`를 필드로 생성해 프로토타입에 전달(`new Resident(ruleHolder)`). "Rule" 메뉴 2개가 `ruleHolder.change(...)` 호출 |
| `Cell`, `Neighborhood`, `Cell.DUMMY` | **변경 없음** (결정 1의 결과) |

`RuleHolder`를 만드는 주체: 처음에는 매개변수 없는 `Resident()` 생성자가 만들었는데, 그러면 `Universe`가 그 객체를 가리키는 참조를 갖지 못해 규칙을 바꿀 수 없었다. `Universe`가 먼저 만들어 필드로 갖고 프로토타입에 넘기도록 했다. 규칙에 관한 코드는 `Resident`에만 있고, 규칙 보관 객체의 생성과 소유는 메뉴를 등록하는 `Universe`가 맡는다.

- 가로 3칸 두 줄을 한 줄 띄워 배치(가운데 빈칸의 이웃이 6개)하고 Tick을 두 번 누르면, Conway에서는 2세대에 전멸하고 HighLife에서는 2세대에 3×3이 된다.

Strategy 패턴을 적용한 효과:

- 규칙을 추가할 때 `Rule` 구현체와 메뉴 항목만 추가하면 된다. `Resident`는 수정하지 않는다. (`ConwayRule` 다음에 `HighLifeRule`을 추가할 때 `Resident`를 건드리지 않았다.)
- 규칙만 따로 테스트할 수 있다. 변경 전에는 규칙을 확인하려면 `Resident`와 이웃 8개를 만들어야 했고(`ResidentTest`의 헬퍼 메서드), 변경 후에는 `rule.nextState(true, 2)` 한 줄이다.

남은 것 / 한계:

- 메뉴에 현재 선택된 규칙이 표시되지 않는다.
- 규칙을 바꿔도 판은 그대로 두고 다음 세대부터 새 규칙을 적용한다.
- A 방식에서 테스트가 서로 영향을 주는 현상은 저장소 밖 실험으로만 확인했다.
