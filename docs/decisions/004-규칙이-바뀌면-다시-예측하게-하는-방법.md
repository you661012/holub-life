# ADR 004 — 규칙이 바뀌었을 때 다시 예측하게 하는 방법

- 날짜: 2026-11-17
- 상태: **확정, 구현 전.** 화면 연결(창 아래 한 줄)을 만들 때 구현한다.
- 관련 코드: `Universe.java`, `RuleHolder.java`

## 1. 문제

창 아래에 현재 규칙과 예측한 결말을 한 줄로 보여 주려고 한다. 예측은 판의 배치와 규칙으로 정해지므로 규칙이 바뀌면 다시 해야 한다.

지금 `RuleHolder.change()`는 규칙을 바꾸기만 하고 누구에게도 알리지 않는다. 규칙을 바꾸는 곳은 `Universe`의 메뉴 세 곳이다(Conway, HighLife, 직접 입력).

**결정할 것: 규칙이 바뀌었다는 것을 예측하는 쪽에 누가 어떻게 전하는가.**

## 2. 검토한 대안

| | 방식 | 고치는 곳 |
|---|---|---|
| 가 | 규칙을 바꾸는 자리마다 "다시 예측하라"를 한 줄씩 적는다 | `Universe`의 세 곳 |
| 나 | `Universe`에 규칙을 바꾸는 메서드를 하나 두고, 그 안에서 규칙 바꾸기와 다시 예측 요청을 함께 한다 | `Universe` |
| 다 | `RuleHolder.change()`가 구독자에게 알린다 (Observer) | `RuleHolder`, `Universe` |

### 가. 자리마다 적는다

- 구현: 메뉴 세 곳의 `ruleHolder.change(...)` 바로 뒤에 다시 예측하라는 호출을 적는다.
- 장점: 새로 만드는 것이 없다.
- 단점: 같은 두 줄이 세 곳에 반복된다. 규칙을 바꾸는 메뉴를 나중에 추가하면서 한 줄을 빠뜨리면 화면의 한 줄이 틀린 채로 남는다.

### 나. `Universe`의 메서드 하나에 모은다

- 구현: `Universe`에 규칙을 받아 바꾸는 메서드를 둔다. 그 메서드가 `ruleHolder.change(rule)`을 부르고 이어서 다시 예측을 요청한다. 메뉴 세 곳은 이 메서드만 부른다.
- 장점: 규칙을 바꾸는 길이 메서드 하나가 된다. `RuleHolder`는 고치지 않는다. 판이 바뀌는 경우(클릭, Clear, Load)도 `Universe`가 처리하므로, 다시 예측을 요청하는 곳이 `Universe` 한 클래스에 모인다.
- 단점: 규칙 변경과 예측을 잇는 책임이 `Universe`에 남는다. 나중의 코드가 이 메서드를 거치지 않고 `ruleHolder.change()`를 직접 부르면 빠진다. `Universe`는 화면과 메뉴를 만드는 코드에 묶여 있어서 이 연결을 화면 없는 단위 테스트로 확인하기 어렵다.

### 다. `RuleHolder`가 알린다 (Observer)

- 구현: `RuleHolder`에 구독하는 메서드를 추가하고 `change()` 안에서 구독자에게 알린다. 원본의 `Publisher`를 쓸 수 있다. `Universe`는 처음에 한 번 구독한다.
- 장점: 규칙을 어디서 바꾸든 통지가 간다. "규칙을 바꾸면 구독자가 통지받는다"를 `RuleHolder`만으로 JUnit에서 확인할 수 있다.
- 단점: `RuleHolder`를 고치고, 구독 관리와 한 단계 거쳐 가는 호출이 생긴다. 확인되는 것은 통지가 간다는 것까지다. `Universe`가 구독을 빠뜨리거나 통지를 받고도 화면을 고치지 않으면 여전히 틀린다. 판이 바뀌는 경우는 통지로 오지 않으므로 `Universe`가 직접 처리해야 하고, 그러면 다시 예측하게 하는 길이 둘(통지와 직접 호출)이 된다.

## 3. 결정 — `Universe`의 메서드 하나에 모은다 (나)

**선택: 나.**

이유:

- 규칙을 바꾸는 곳이 전부 `Universe` 안에 있다. `ruleHolder.change(...)`를 부르는 곳은 `Universe`의 세 곳뿐이고, `ruleHolder`는 `Universe`의 `private final` 필드다. 다가 막아 주는 "어디서 바꾸든"의 위험이 지금은 `Universe` 한 클래스 안의 일이다.
- 판이 바뀌는 경우도 `Universe`가 처리한다. 나를 고르면 다시 예측을 요청하는 곳이 한 클래스에 모인다. 다를 골라도 판이 바뀌는 쪽은 직접 호출로 남는다.

정한 뒤에 확인한 장점 (정할 때 쓴 이유는 아니다):

- 흐름을 따라가기 쉽다. 메뉴 → `Universe`의 메서드 → 규칙 변경과 예측 요청으로 이어지는 호출이 코드에 그대로 보인다.

돌려 본 것: 세 방법을 작게 만들어(`docs/experiments/RuleChangeDemo.java`), 가로 3칸 두 줄을 놓고 메뉴를 차례로 고른 것처럼 호출했다. 가에는 나중에 추가한 메뉴에서 한 줄을 빠뜨린 상황을 일부러 넣었다.

| 고른 메뉴 | 가 (한 줄 빠뜨림) | 나 | 다 |
|---|---|---|---|
| 처음 | Conway, 2세대 뒤 소멸 | 같음 | 같음 |
| HighLife | HighLife, 11세대 뒤 소멸 | 같음 | 같음 |
| 직접 입력 `B3/S23` | HighLife, 11세대 뒤 소멸 (틀림) | 직접 입력, 2세대 뒤 소멸 | 직접 입력, 2세대 뒤 소멸 |

가의 틀린 결과는 호출이 여러 곳에 흩어져 있을 때의 위험을 보여 준다. 직접 부르는 방식 전체가 틀린다는 뜻은 아니다. 나는 빠뜨릴 자리를 하나로 줄인다.

"다시 예측을 요청한다"와 "그 자리에서 끝까지 계산한다"는 다르다. 이 결정은 요청을 누가 하느냐까지만 정한다. 계산을 어느 스레드에서 할지는 따로 정한다. `Publisher.publish()`는 스레드를 새로 만들지 않고 부른 쪽의 스레드에서 구독자를 차례로 부르므로, 다를 골라도 이 문제는 그대로 남는다.

수업 자료와의 관계:

- `15 Mediator` 15쪽은 Mediator와 Observer를 나란히 비교한다. Mediator는 통신을 한곳에 모아 흐름을 이해하기 쉽지만 다시 쓰기 어렵다. Observer는 통신을 나눠 주어 다시 쓰기 쉽지만 흐름을 이해하기 어렵다.
- 원본의 `Universe`는 주석에서 스스로를 Swing의 이벤트와 Life 클래스들 사이의 mediator라고 부른다. 나는 `Universe`가 원래 하던 방식을 그대로 따른다.
- `21 Pattern Hatching` 53쪽은 패턴에 비용(간접 호출, 복잡도)이 있으니 필요한 만큼만 유연하게 설계하라고 한다.

포기한 것:

- 규칙을 어디서 바꾸든 통지가 가는 것.
- 통지가 간다는 것을 `RuleHolder`만으로 JUnit에서 확인하는 것.

다시 볼 때: 규칙을 바꾸는 곳이 `Universe` 밖에 생기면 다를 다시 검토한다.

## 4. 결정에 이른 과정

1. 처음에는 가와 다 둘만 놓고 작게 돌려 봤다. 가에 일부러 한 줄을 빠뜨렸고, 그 결과만 보면 다가 나아 보였다.
2. 다시 검토하면서 빠진 대안(나)이 있다는 것을 알았다. 가에서 한 줄을 빠뜨린 실험은 직접 부르는 방식 전체가 불리하다는 증거가 아니었다.
3. 셋을 같이 돌려 보니 나도 다와 같은 결과를 냈다.
4. 규칙을 바꾸는 곳을 코드에서 찾아보니 세 곳 모두 `Universe` 안이었다.
5. 다의 테스트가 보증하는 범위도 다시 봤다. 통지가 가는 것까지이고 화면 연결까지는 아니다.
6. 나로 정했다.

## 5. 구현 결과

아직 구현하지 않았다. 화면 연결과 함께 구현하고 그때 이 절을 채운다.

남은 것:

- 예측 계산을 어느 스레드에서 할지. 세대 진행은 `Clock`의 타이머 스레드에서, 메뉴와 클릭은 Swing의 스레드에서 처리된다.
- 세대가 진행되는 중에 어느 시점의 판과 규칙으로 예측할지.
- 예측의 한도를 몇 세대로 할지.
