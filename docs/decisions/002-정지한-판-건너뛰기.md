# ADR 002 — 정지한 판에서 규칙 변경이 반영되지 않는 문제를 고치는 방식

- 날짜: 2026-11-16
- 상태: **확정, 구현 완료** (2026-11-16)
- 관련 코드: `Neighborhood.java`, `NeighborhoodRuleTest.java`

## 1. 문제

확장 1에서 실행 중에 규칙을 바꿀 수 있게 만들었다. 그런데 판이 정지한 뒤에는 규칙을 바꿔도 반영되지 않았다. 여기서 정지한 판은 Go > Halt로 멈춘 판이 아니라 모든 세포가 더 변하지 않게 된 판이다. 테스트 이름에서는 "조용해진 판"이라고 불렀다.

재현 방법은 다음과 같다. Conway 규칙으로 Ship을 놓는다.

```
■ ■ □
■ □ ■
□ ■ ■
```

Ship은 Conway에서 변하지 않는 모양이다. 가운데 빈칸의 이웃이 6개인데 Conway에서는 이웃이 3개일 때만 세포가 태어난다. 여기서 규칙을 HighLife로 바꾸면 이웃이 6개인 빈칸에서도 세포가 태어나므로 가운데 칸이 살아나야 한다. 하지만 Ship은 정지한 채로 그대로 있었다.

원인은 `Neighborhood.figureNextState()` 앞부분에 있던 조건이다.

```java
if(     amActive
    ||  north.isDisruptiveTo().the( Direction.SOUTH )
    ||  south.isDisruptiveTo().the( Direction.NORTH )
    // 나머지 여섯 방향도 같은 모양
)
{
    // 구역 안의 칸마다 figureNextState()를 호출한다
}
```

이 구역에서도, 맞닿은 옆 구역의 가장자리에서도 직전 세대에 변한 세포가 없으면 계산을 통째로 건너뛴다. 이전 세대에 변화가 없었으니 이번에도 같을 것이라고 보는 것이다. 규칙이 하나로 고정된 원본에서는 맞는 생각이다. 하지만 규칙이 바뀌면 이전에 변화가 없었더라도 변화가 있을 수 있다.

**결정할 것: 정지한 판에서도 규칙을 바꾸면 다음 세대부터 반영되게 하려면 어디를 어떻게 고칠 것인가.**

## 2. 검토한 대안

| | 방식 | 고치는 곳 |
|---|---|---|
| 가 | 건너뛰는 조건을 없앤다 | `Neighborhood` 한 곳 |
| 나 | 건너뛰기는 두고, 판을 깨우는 메서드를 `Cell` 인터페이스에 추가해서 규칙을 바꿀 때 호출한다 | `Cell`, `Cell.DUMMY`, `Neighborhood`, `Resident`, `Universe` 다섯 곳 |
| 다 | 원본은 고치지 않고, `Universe`가 규칙을 바꿀 때 `userClicked()` 등으로 판을 건드려 깨운다 | `Universe` 한 곳 |

### 가. 건너뛰는 조건을 없앤다

- 구현: 위의 `if` 조건을 지운다. 매 세대 모든 `Resident`가 다음 상태를 계산한다.
- 장점: `Neighborhood` 한 곳만 고친다. 규칙을 바꾸는 쪽에서 따로 할 일이 없으니 빠뜨릴 것도 없다.
- 단점: Holub이 넣어 둔 건너뛰기 최적화가 없어진다. 그동안 고치지 않던 원본 `Neighborhood`를 고치게 된다.

### 나. 판을 깨우는 메서드를 `Cell`에 추가한다

- 구현: `Cell` 인터페이스에 판을 깨우는 메서드를 추가한다. `Neighborhood`는 안쪽 칸들에게 같은 호출을 넘긴다. 원본의 `clear()`와 같은 위임이다. `Universe`는 규칙을 바꿀 때마다 이 메서드를 호출한다.
- 장점: 건너뛰기 최적화가 그대로 남는다.
- 단점: 다섯 곳을 고친다. `Cell`에 메서드가 생기면 `Resident`와 `Cell.DUMMY`도 그 메서드를 구현해야 한다. 규칙을 바꾸는 메뉴가 늘어날 때 깨우는 호출을 빠뜨리면 같은 문제가 다시 생긴다. `Universe`는 화면과 메뉴를 만드는 코드에 묶여 있어서, 규칙을 바꿀 때 실제로 깨우는지를 화면 없는 단위 테스트로 확인하기 어렵다. 그 테스트는 쓰지 않았다. (처음에는 "JUnit으로 확인할 수 없다"고 적었는데 과한 말이었다. 11/17 정정)

### 다. `Universe`가 판을 건드려 깨운다

- 구현: 원본은 고치지 않는다. `Universe`가 규칙을 바꿀 때 `userClicked()` 등을 호출해서 `Neighborhood`가 다시 계산하게 만든다.
- 장점: 원본 클래스를 하나도 고치지 않는다.
- 단점: `userClicked()`는 세포를 켜고 끄는 메서드라서 원래 용도와 다르게 쓰게 된다. 이 방법으로 확실히 깨워지는지도 확인하지 못했다. 11/12에 규칙을 바꾼 뒤 판을 클릭해 보는 실험을 두 번 했는데, 한 번은 그대로였고 한 번은 한 세대 늦게 반영됐다. `Universe` 쪽 연결을 화면 없는 단위 테스트로 확인하기 어려운 것은 나와 같다.

## 3. 결정 — 건너뛰는 조건을 없앤다 (가)

**선택: 가.**

이유:

- 전부 계산하는 데 드는 시간이 작았다. 건너뛰기가 있을 때와 없을 때를 나란히 잰 것은 아니고, 전부 계산하게 되는 경우의 시간을 잰 것이다 (11/17 정정). 4,096칸을 전부 계산하는 데 걸린 시간은 Blinker 하나만 있는 판에서 세대당 0.085ms, 판의 30%를 무작위로 채운 판에서 0.17ms였다. 가장 빠른 속도(Go > Fast)의 세대 간격이 30ms다.
- 건너뛰기는 판 전체가 정지했을 때만 작동하고 있었다. 빈 판과 Ship만 있는 판에서는 계산한 칸이 세대당 0개였지만, Blinker 하나만 있어도 4,096칸을 전부 계산했다. 세포가 하나라도 움직이는 판에서는 원래도 전부 계산하고 있었다.
- 재현 테스트를 고치지 않아도 된다. 가에서는 테스트가 그대로 통과한다. 나에서는 테스트 안에 깨우는 호출을 넣어야 통과한다.
- `Cell` 인터페이스에 메서드를 더하지 않는다. ADR 001의 결정 1은 규칙에 관한 것을 `Cell`에 드러내지 않는다는 것이었다. 나의 메서드는 ADR 001의 D(`setRule()`)와 같지는 않다. `setRule()`은 규칙을 넘기는 것이고 깨우는 것은 다시 계산하라는 것이다. 그래도 규칙을 바꾸는 기능 때문에 `Cell`에 메서드가 늘어난다는 점은 D와 같다.

잰 방법: `Rule.nextState()`가 불린 횟수를 세는 `Rule` 구현체를 끼우고, 화면 없이 `Universe`의 `tick()`과 같은 방식으로 세대를 진행했다. 두 번 실행했다. 세대 간격은 `Clock.java`에 적힌 값이다.

수업 자료와의 관계 (13 Composite, 51쪽 "Where to place Child Mgt. Interface?"):

- 이 구조에서 `Cell`은 Component, `Resident`는 Leaf, `Neighborhood`는 Composite다.
- 슬라이드는 Composite에만 필요한 자식 관리 메서드를 어디에 둘지를 다룬다. Component에 두면 Leaf와 Composite를 똑같이 다룰 수 있다(Transparency). 대신 Leaf에게 의미 없는 호출을 할 수 있게 된다. Composite에만 두면 그런 호출이 컴파일 단계에서 막힌다(Safety). 대신 둘의 인터페이스가 달라진다.
- 나의 깨우는 메서드는 자식을 관리하는 메서드는 아니다. 하지만 Composite에만 의미가 있다는 점은 같다. 건너뛸지를 정하는 `amActive`는 `Neighborhood`의 필드이고 `Resident`에는 깨울 것이 없다. 이 메서드를 `Cell`에 두면 `Resident`와 `Cell.DUMMY`는 아무 일도 하지 않는 메서드를 갖게 된다. 나는 Transparency 쪽의 선택이고 이것이 그 대가다.
- ADR 001의 `setRule()`은 Leaf(`Resident`)에만 의미가 있는 메서드였다. 이번 메서드는 Composite(`Neighborhood`)에만 의미가 있어서 방향이 반대다. 두 번 다 `Cell`에 메서드를 더하지 않는 쪽을 골랐다.
- 가는 `Cell`을 고치지 않으므로 이 문제가 생기지 않는다.

포기한 것:

- Holub의 건너뛰기 최적화. 판 전체가 정지해 있을 때도 매 세대 4,096칸을 계산한다.
- 원본 `Neighborhood`를 그대로 두는 것. ADR 001 때는 변경 없는 클래스였는데 이번에 처음 고쳤다.

## 4. 결정에 이른 과정

1. 11/12에 정지한 판에서는 규칙을 바꿔도 반영되지 않는 것을 발견했다. 그 전까지는 계속 움직이는 판에서만 규칙 교체를 시험했다.
2. 처음에는 나가 유력해 보였다. 건너뛰기 최적화를 그대로 둘 수 있어서다.
3. 그 최적화가 실제로 얼마나 아끼는지 모르고 있었다. 그래서 재 보고 정하기로 했다.
4. 재 보니 건너뛰기는 판 전체가 정지했을 때만 작동했고, 전부 계산해도 세대당 0.2ms가 안 됐다. 가로 정했다.
5. 정한 뒤에 나가 수업 13 Composite의 Transparency 대 Safety와 같은 종류의 문제라는 것을 연결했다. 결정할 때 쓴 이유는 아니다.

## 5. 구현 결과 (2026-11-16)

`Neighborhood.figureNextState()`에서 건너뛰는 `if` 조건 열 줄을 지웠다 (커밋 `7e783f7`). 새로 쓴 코드는 없다.

`amActive`, `activeEdges`, `isDisruptiveTo()`는 지우지 않았다. `amActive`는 `figureNextState()`의 반환값과 `redraw()`에서 계속 쓰인다.

테스트 (`./gradlew test`, 42개 통과):

- 재현 테스트 `조용해진_판에서도_규칙을_바꾸면_다음_세대부터_반영된다`를 추가했다. Ship을 Conway로 3세대 진행한 뒤 HighLife로 바꾸고, 세포 수가 6에서 7, 4, 0으로 바뀌는지 본다. 고치기 전에는 `expected: <7> but was: <6>`으로 실패했고 고친 뒤에는 통과한다.
- 나머지 41개는 수정 없이 통과한다.

실제 프로그램에서 확인 (`./gradlew run`):

- Ship을 놓고 Go > Agonizing으로 돌리다가 Rule을 HighLife로 바꾸자 Ship이 사라졌다.

남은 것 / 한계:

- 계산 시간과 계산한 칸 수는 저장소 밖의 실험 코드로만 쟀다. JUnit 테스트로는 남기지 않았다.

## 6. 나중에 바로잡은 것 (2026-11-24)

3절의 이유 둘째 줄("건너뛰기는 판 전체가 정지했을 때만 작동하고 있었다")은 원본의 다른 버그 때문에 생긴 현상이었다.

- 원본 `Resident.transition()`은 상태가 바뀌지 않은 칸에도 `true`를 돌려줬다. 11/17에 이것을 고쳤다(`docs/findings.md` 1번, 확장 2 문서). `Neighborhood.transition()`은 이 값이 `true`인 가장자리 칸을 "변했다"고 표시하므로, 세포가 하나라도 움직여 판의 `transition()`이 불리는 세대에는 모든 구역의 가장자리가 표시됐다. 그래서 다음 세대에 모든 구역이 계산했다.
- 건너뛰기 조건을 되살린 사본으로 다시 쟀다(`docs/experiments/skip-check/run.sh`). Blinker 하나만 있는 판에서 2세대부터 계산한 칸 수는, 원본 `transition()`이면 4,096칸, 고친 `transition()`이면 64칸(Blinker가 있는 구역 하나)이었다. Ship만 있는 판은 둘 다 0칸이었다.
- 따라서 지금 코드에서 건너뛰기를 되살렸다면, 움직이는 곳이 판의 일부뿐일 때 계산을 크게 줄였을 것이다. 이 결정에서 포기한 것은 처음 생각한 것보다 크다.

결정(가)은 바꾸지 않는다. 이유:

- 전부 계산하는 데 드는 시간(세대당 0.085~0.17ms)이 가장 빠른 세대 간격(30ms)에 비해 작다는 이유는 그대로 성립한다.
- 재현 테스트가 그대로 통과하고 `Cell`에 메서드를 더하지 않는다는 이유도 그대로다.
- 이 사실을 안 것은 코드 동결(11/23) 뒤다.

다시 볼 때: 판이 커지거나 세대 간격이 짧아져 계산 시간이 문제가 되면 나를 다시 검토한다. 지금은 규칙을 바꾸는 길이 `Universe.changeRule()` 하나로 모였으므로(ADR 004), 나의 단점이던 "깨우는 호출을 빠뜨릴 위험"도 처음보다 작다.
