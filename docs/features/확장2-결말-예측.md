### 4-1. 구현하면서 정한 것과 이유

ADR로 쓸 만한 갈림길은 아니고 코드를 쓰면서 정한 것들이다 (11/17).
"고르지 않은 것"은 떠올린 다른 방법이다. 따로 재 본 것은 속도뿐이고 나머지는 재 보지 않았다.

**`Generation` (한 세대에 살아 있는 칸들의 좌표)**

| 정한 것 | 이유 | 고르지 않은 것, 대가 |
|---|---|---|
| 좌표를 담은 객체가 스스로 다음 세대를 만든다 (`generation.next(rule)`) | 예측기가 지나온 세대를 하나씩 들고 비교한다. 세대 하나가 객체 하나인 편이 쓰기 쉽다. 좌표와 그 좌표로 하는 계산이 한 클래스에 있다 | 좌표와 계산을 떼어 `계산기.next(좌표들, rule)`로 두는 것 |
| 한 번 만들면 바뀌지 않는다. `next`는 새 객체를 돌려준다 | 예측기가 지나온 세대를 `Map`의 키로 기억한다. 키가 나중에 바뀌면 찾을 수 없다 | 자기 자신을 다음 세대로 바꾸는 것. 대가는 세대마다 객체를 새로 만드는 것 |
| 생성자가 판 크기를 받는다 (`new Generation(좌표들, 64)`) | 64는 `Universe`의 상수 둘(구역 8칸 × 구역 8개)에서 나오는 값이다. `Generation`에도 적으면 같은 숫자가 두 곳에 생긴다 | 64를 `Generation`의 상수로 두는 것 |
| 판 밖 좌표가 들어오면 `IllegalArgumentException` | 벽 처리가 "판 밖 좌표는 들어 있지 않다"에 기대고 있다. 조용히 틀린 답을 내는 대신 만들 때 바로 실패한다. `BirthSurvivalRule`의 생성자와 같은 방식이다 | 판 밖 좌표를 말없이 버리는 것 |
| 판의 모든 칸(4096칸)을 매 세대 본다 | 이웃이 0개여도 태어나는 규칙(`B0`)에서도 맞다. 실제 판도 세대마다 모든 `Resident`가 계산한다 (ADR 002) | 살아 있는 칸과 그 둘레만 보는 것. 대가는 속도다. 500세대를 진행만 시켰을 때 약 0.19초(Blinker 하나)에서 0.35초(무작위 30%)가 걸렸다. 같은 조건에서 `Neighborhood` 판은 약 0.04초에서 0.06초였다 (저장소 밖에서 쟀다. ADR 003의 6절) |
| 좌표는 `java.awt.Point`의 `Set`으로 든다 | 원본의 `Cell.Memento`가 `Point`로 좌표를 주고받는다. 판에서 읽은 좌표를 바꾸지 않고 넘길 수 있다 | `boolean[][]` 배열, 좌표 클래스를 새로 만드는 것 |
| 받은 집합과 그 안의 좌표 객체(`Point`)를 복사해 둔다. `liveCells()`도 복사본을 돌려준다 | `java.awt.Point`는 x, y를 고칠 수 있는 객체다. 그대로 들고 있으면 넘겨준 쪽이나 받아 간 쪽이 `Point`를 고칠 때 `Generation`도 바뀐다. 처음에는 집합만 복사했는데(`Set.copyOf`) 그것으로는 `Point`가 고쳐지는 것을 막지 못했다. 재현 테스트 둘을 추가하고 고쳤다 (11/17) | 받은 것을 그대로 드는 것, 집합만 복사하는 것. 대가는 만들 때와 꺼낼 때마다 `Point`를 새로 만드는 것 |
| 비었는지만 묻는 `isEmpty()`를 둔다 | `liveCells()`가 복사본을 만들게 되어, 예측기가 세대마다 비었는지 물을 때 복사하지 않게 했다 | `liveCells().isEmpty()`로 묻는 것 |
| `equals`와 `hashCode`를 둔다 | 전에 본 모양인지 비교하고 `Map`의 키로 쓰려면 필요하다. 판 크기와 살아 있는 칸이 같으면 같은 `Generation`이다 | |

**`EndingPredictor`와 `Ending` (결말 판정)**

| 정한 것 | 이유 | 고르지 않은 것, 대가 |
|---|---|---|
| `Ending`은 클래스 하나에 종류(`Kind`), 몇 세대 뒤(`after`), 주기(`period`)를 담는다 | 결말을 쓰는 곳이 화면의 글자 한 줄뿐이라 가장 단순한 모양으로 했다 | 결말 종류마다 클래스를 두는 것. 대가는 소멸과 미확정에서 `period`가 뜻 없는 0이라는 것 |
| 빈 판이 다음 세대에도 빈 판일 때만 소멸이다. 이것을 정지보다 먼저 본다 | 비어서 멈춘 판도 다음 세대와 같은 모양이라, 순서를 정하지 않으면 정지로 나온다. "다음 세대에도 빈 판"이라는 조건은 나중에 넣었다. 처음에는 빈 판이면 바로 소멸이라고 답하게 짰는데, 이웃이 0개여도 태어나는 규칙(`B0`)에서 틀렸다. 빈 판을 `B0/S`로 돌리면 실제 판은 0 → 4096 → 0칸으로 되풀이되는데 예측기는 소멸이라고 했다. 재현 테스트를 먼저 추가하고 고쳤다 (11/17) | 빈 판이면 바로 소멸로 답하는 것 (틀린다). 대가는 빈 판을 만났을 때 다음 세대를 한 번 더 계산하는 것 |
| 정지의 주기는 1, 반복의 주기는 2 이상 | 정지를 "한 세대 만에 같은 모양으로 돌아오는 것"으로 보면, 정지와 반복을 같은 계산(지금 세대 번호 − 처음 본 세대 번호)으로 가를 수 있다 | |
| `after`는 그 모양이 처음 나온 세대다 | "몇 세대 뒤에 멈춘다", "몇 세대 뒤부터 되풀이된다"를 말하려면 다시 나온 때가 아니라 처음 나온 때가 필요하다 | 같은 모양을 다시 본 세대를 돌려주는 것 |
| 한도는 생성자로 받는다. 뜻은 "미리 돌리는 세대 수"다 | 테스트에서 작은 한도로 미확정을 만들 수 있고, 숫자를 코드에 박지 않는다. 정지는 그다음 세대와 같다는 것을 봐야 알므로, 247세대에 멈추는 모양은 한도가 248이어야 정지로 나온다. 소멸은 다르다. 빈 판을 만나면 계속 비어 있는지 보려고 다음 세대를 계산하는데, 이 확인용 계산은 한도에 넣지 않는다. 한도 세대에 판이 비었을 때도 소멸인지 확정할 수 있게 하려는 것이다 (테스트 `소멸은_한도_세대에_판이_비어도_알_수_있다`). 이 테스트는 한도에 닿은 Conway의 소멸 결과를 고정할 뿐이고 계산 횟수를 세지는 않는다. `B0`처럼 빈 판에서 다시 태어나는 규칙에서는 빈 판을 만날 때마다 확인용 계산과 진행용 계산을 따로 한다 | 한도를 상수로 두는 것. 빈 판 확인도 한도에 넣는 것 (한도 세대에 비면 미확정이 된다) |
| 지나온 세대를 `Map<Generation, Integer>`에 기억한다 | 전에 본 모양인지와 그때가 몇 세대였는지를 한 번에 찾는다 | 직전 세대 하나만 기억하는 것 (정지만 알 수 있고 반복은 모른다) |
| 이동은 알아보지 않는다 | 판이 64칸으로 막혀 있어 날아가는 모양도 끝에 닿으면 멈추거나 사라진다. 그때까지 미리 돌리면 결말이 나온다 (Glider는 247세대 뒤 정지) | 위치만 옮겨 간 같은 모양을 알아보는 것 |
| 메서드와 `Kind` 값의 이름은 영어로 쓴다 | 기존 코드와 맞춘다 | |

**화면 연결 (`Universe`, `PredictionRequest`, `PredictionWorker`, `StatusLine`, `LiveCellCollector`)**

잠금, 작업자, 옛 계산을 다루는 방법은 ADR 005에, 규칙 변경을 `Universe`의 메서드 하나에 모은 것은 ADR 004에 적었다. 아래는 그 밖에 코드를 쓰면서 정한 것이다 (11/17).

| 정한 것 | 이유 | 고르지 않은 것, 대가 |
|---|---|---|
| 한도는 500세대 (`Universe.PREDICTION_LIMIT`) | 지금까지의 테스트와 실험 숫자가 모두 500으로 잰 것이다. 실제 판에서 확인한 가장 늦은 결말(Glider, 247세대 뒤 정지)을 담는다 | 대가: 결말이 안 나오는 판은 500세대를 다 계산한다 |
| 한 줄은 창의 아래 칸(`BorderLayout.SOUTH`)에 둔다. 글자 칸(`JLabel`)은 `Universe`가 만들어 내주고 `Life`가 붙인다 | 창에서 `CENTER`만 쓰이고 있었다. `Universe`는 판을 직접 그리는 패널이라 그 안에 글자 칸을 넣기 어렵다. 글자를 고치는 쪽이 `Universe`라서 `Universe`가 들고 있다 | `Life`가 글자 칸을 만들어 `Universe`에 넘기는 것 |
| 글자는 영어로 쓴다 | 기존 메뉴와 직접 입력 창이 영어다 | |
| 규칙 이름은 규칙 객체의 `toString()`이 B/S 표기로 돌려준다 | `toString()`은 모든 객체에 이미 있는 메서드라 `Rule` 인터페이스와 `Resident`를 고치지 않는다 | `Rule`에 이름을 돌려주는 메서드를 추가하는 것 (구현체를 전부 고쳐야 한다). `Universe`가 메뉴마다 이름을 따로 기억하는 것 |
| 한 줄의 글자를 만드는 일은 `StatusLine`에 따로 둔다. Swing을 쓰지 않는다 | 옛 결과를 버리는 것과 남은 세대를 줄이는 것을 화면 없이 JUnit으로 확인한다. `Universe`는 화면에 묶여 있어 그렇게 확인하기 어렵다 | 이 계산을 `Universe` 안에 두는 것 |
| `PredictionWorker`는 계산하는 것과 결과를 받는 쪽을 생성자로 받는다 | 테스트에서 진짜 예측기 대신, 테스트가 정한 때에 끝나는 가짜 계산을 넣는다. 시간을 재지 않고 "A 계산 중에 B, C가 오면 C만 계산한다"를 확인한다 | `PredictionWorker`가 `EndingPredictor`를 직접 드는 것 |
| 작업자 스레드는 데몬 스레드다 | 예측을 계산하는 중이어도 프로그램이 끝나는 것을 막지 않는다 | |
| 계산이 예외로 실패하면 그 요청만 버리고 다음 요청을 계산한다 | 한 번 실패했다고 작업자가 멈추면 그 뒤로 한 줄이 계속 "계산 중"으로 남는다 (테스트 `계산이_실패해도_다음_요청은_계산한다`) | 대가: 실패한 요청의 한 줄은 다음 변경이 있을 때까지 "계산 중"으로 남는다 |
| 세대 번호는 시계가 한 번 울릴 때마다 1 올린다. 판이 변하지 않은 세대에도 올린다 | 정지한 판도 세대는 지나간다. 남은 세대를 세는 기준이 끊기지 않는다 | 판이 변한 세대에만 올리는 것 |
| 세대 번호는 Clear와 Load 때 0으로 되돌린다. 클릭과 규칙 변경 때는 그대로 둔다 | Clear와 Load는 새 판을 시작하는 것이고, 클릭과 규칙 변경은 진행 중인 판을 고치는 것이다 | 한 번도 되돌리지 않는 것 |
| 세포 수는 세대마다 판을 읽어서 센다 (`readBoard()`를 예측 요청과 같이 쓴다) | 판을 읽는 코드를 한 벌만 둔다. `Neighborhood.isAlive()`는 항상 `true`라 세는 데 쓸 수 없다 | 대가: 세대마다 4096칸을 훑고 좌표를 복사한다. 이 시간은 재지 않았다 |
| `Generation`에 `liveCount()`를 추가했다 | `liveCells()`는 복사본을 만든다. 수만 필요할 때 복사하지 않게 했다 | `liveCells().size()` |
| `StatusLine`은 지금보다 낮은 변경 번호로 온 판 정보를 무시한다 | 세대 진행(시계 스레드)이 읽은 정보는 Swing 스레드로 넘겨져 나중에 반영된다. 그사이에 클릭이 먼저 반영되면 클릭 전의 정보가 뒤늦게 도착한다. 그것을 받아들이면 변경 번호가 뒤로 가서 새 예측 결과가 버려진다 (테스트 `늦게_도착한_옛_세대_정보는_무시한다`) | |
| 결과의 기준 세대가 한 줄의 세대보다 앞서 있으면 지나간 세대를 0으로 본다 | 결과가 세대 정보보다 먼저 도착하는 짧은 순간에 남은 세대가 예측보다 크게 나오지 않게 한다. 곧 도착하는 세대 정보가 바로잡는다 | |
| 미확정은 세대가 지나도 그대로 둔다 | 미확정은 "기준 세대부터 500세대 안에는 결말이 없다"는 뜻이라 줄여 갈 남은 세대가 없다 | 500세대가 지나면 다시 예측하는 것. 대가: 판이나 규칙을 바꾸기 전에는 미확정이 계속 떠 있다 |
| 프로그램을 켰을 때의 빈 판도 예측한다 | 처음부터 한 줄에 네 칸이 다 채워진다 | 첫 클릭 전에는 예측 칸을 비워 두는 것 |
| Load는 잠금을 두 번 잡는다 (판 비우기 / 읽은 내용 넣기). 그 사이에 파일을 읽는다 | 파일을 읽는 동안에는 잠금을 잡지 않는다 (ADR 005). 판을 비운 뒤 파일 읽기가 실패해도 비운 판으로 한 줄을 고친다 | 파일 읽기까지 잠금 하나에 넣는 것 |
| 새 코드에서 눌렸을 때·끝났을 때 실행할 코드는 람다(`() -> …`)로 적었다 | 원본의 `new Runnable() { … }`와 같은 일을 하고 짧다. 원본의 코드는 바꾸지 않았다 | 원본처럼 익명 클래스로 적는 것 |
| 한 줄을 두 줄로 나눴다. 윗줄은 세대 수·세포 수·규칙, 아랫줄은 예측한 결말이고 아랫줄만 16pt로 키웠다 (11/17, 머지 뒤에 고침) | 한 줄로 두면 창 너비(512px)를 넘는 문장이 있었다. 13pt에서 `repeats (period 12) in 499 generations`가 든 줄이 585px였다. 넘친 글자는 끝이 `...`으로 잘린다. 창을 띄우지 않고 글자만 읽어 확인해서 처음에는 몰랐다. 나눈 뒤에는 가장 긴 윗줄이 409px, 가장 긴 아랫줄이 376px이고 글자 칸의 너비는 496px다 (`docs/experiments/Fit.java`) | 글자를 줄이는 것, 문장을 짧게 바꾸는 것. 대가: 창이 글자 한 줄만큼 더 길어진다 |
| 글자 칸은 글자가 바뀌어도 배치를 다시 하라고 요청하지 않는다 (`Universe.FixedLabel`이 `revalidate()`를 비워 둔다. 11/17, 머지 뒤에 고침) | 창을 키운 채 클릭하면 판이 번쩍였다. `JLabel`은 글자가 바뀔 때마다 창의 배치를 다시 하라고 요청한다. 그러면 창이 판을 가운데 칸 크기로 늘리고, 원본 `Universe`의 `componentResized`가 판을 곧바로 정사각형으로 줄인다. 창이 기본 크기일 때는 두 크기가 같아서 보이지 않았다. 클릭 5번에 배치가 무효가 된 횟수가 5에서 0이 됐다 (`docs/experiments/Flicker.java`). 이 글자 칸은 가로로 꽉 차고 높이가 정해져 있어 배치를 다시 할 필요가 없다 | 원본의 `componentResized`를 고치는 것 (창 크기를 바꿀 때의 동작이 달라질 수 있다) |
| 아랫줄의 글자색을 결말의 종류로 정한다. 소멸은 빨강, 정지는 파랑, 반복은 초록, 미확정과 계산 중은 회색 (11/17, 머지 뒤에 넣음) | 규칙이나 판을 바꿨을 때 결말의 종류가 달라진 것이 글자를 읽기 전에 색으로 보인다. 어떤 결말이 어떤 색인지는 `StatusLine.endingColor()`에 두어 JUnit으로 확인한다. 아직 그 세대에 이르지 않았을 때도 같은 색이다 | 이르기 전과 이른 뒤의 색을 다르게 하는 것. 색을 `Universe`에서 정하는 것 (화면 없이 확인하기 어렵다). 대가: `StatusLine`이 `java.awt.Color`를 쓴다. Swing은 여전히 쓰지 않는다 |
| 창을 띄우지 않고 클릭·세대 진행·메뉴를 흉내 내 한 줄을 읽어 봤다 (`docs/experiments/StatusCheck.java`) | `Universe`의 연결은 JUnit으로 확인하지 못한다. 결과: Glider 5칸 → `still in 247 generations`, 3세대 뒤 `still in 244 generations`, 253세대에 `still`, Clear 뒤 `extinct` | 실제 창에서 눈으로 보는 것은 따로 해야 한다 |

## 6. 한계와 남은 것

### 왜 미리 돌려 보는가, 왜 "미확정"이 있는가

결말을 미리 돌려 보지 않고 계산식으로 바로 아는 방법이 있는지 따져 봤다 (11/17).

- Conway의 Life Game은 튜링 완전하다고 알려져 있다. 세포 배치만으로 임의의 계산을 흉내 낼 수 있다는 뜻이다. 그래서 끝없이 넓은 판에서 "이 배치가 결국 어떻게 되는가"를 돌려 보지 않고 아는 일반적인 방법은 없다 (정지 문제와 같은 문제가 된다).
- 이 프로그램의 판은 64×64칸으로 막혀 있다. 가능한 배치의 수가 유한하므로 충분히 오래 돌리면 전에 본 모양이 반드시 다시 나오고, 답은 원리적으로 항상 구할 수 있다. 다만 돌려 보지 않고 바로 아는 일반적인 지름길은 알려진 것이 없다. "불가능하다고 증명됐다"가 아니라 "알려진 방법이 없다"이다.
- 지름길이 있는 것은 특수한 경우다. 아무것도 태어나지 않는 규칙에서는 세포가 늘지 않는다. `B/S`는 어떤 배치든 1세대 뒤에 소멸한다. 판 전체가 이름 붙은 모양 하나일 때는 표에서 찾을 수 있다. 이런 경우를 따로 처리하지는 않았다.
- Hashlife처럼 되풀이되는 부분을 기억해 빨리 돌리는 알고리즘이 있다. 이것도 돌려 보는 방법을 빠르게 한 것이다. 쓰지 않았다.

그래서 미리 돌려 보는 방법을 썼고, 한도(500세대) 안에 결말이 안 나오면 "미확정"으로 답하게 했다.

> 위의 튜링 완전성, 정지 문제, Hashlife는 수업 슬라이드에 있는 내용이 아니다. 출처를 아직 확인해 달지 않았다. 보고서에 쓰기 전에 출처를 확인한다.
