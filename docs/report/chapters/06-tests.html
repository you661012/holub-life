6. 테스트 수행 내역

JUnit 테스트 113개가 모두 통과한다. 원본 동작이 그대로인지, 확장한 기능이 맞게 동작하는지, 구조를 바꾼 뒤에도 결과가 같은지를 나눠 확인한다.

테스트는 기능보다 먼저 쓰는 것을 원칙으로 했다. 원본 동작 테스트(ResidentTest)는 구조를 바꾸기 전에 썼고 새 클래스도 테스트를 먼저 쓰고 실패를 본 뒤 구현하는 것을 원칙으로 했다. 결함을 고칠 때는 재현 테스트가 실패하는 것을 먼저 확인했다. 처음부터 통과한 테스트는 실제로 잘못을 잡는지 알 수 없어서 중요한 비교 테스트는 코드를 일부러 틀리게 고쳐 실패하는 것을 한 번씩 확인했다.

6-1. 테스트 구성

테스트는 JUnit 6(Jupiter)으로 작성했고 클래스 17개, 테스트 메서드 113개다. 모두 src/test/java/com/holub/life/에 있다. 아래 표는 기존 기능, 확장 1(규칙 선택), 확장 2(결말 예측과 자동 정지) 순으로 묶었다.

RuleToStringTest는 규칙 클래스를 시험하지만 확장 2로 옮겼다. 규칙의 toString()은 창 아래 윗줄의 Rule 칸에 띄우려고 화면 연결 때 추가한 것이기 때문이다. ResidentTransitionTest는 원본 클래스 Resident가 Cell 인터페이스의 약속을 지키는지 보는 테스트라 기존 기능에 두었다. 다만 원본 코드는 이 약속과 반대로 값을 돌려주고 있었고 이 테스트는 그것을 고친 뒤의 동작을 확인한다.

6-2. 테스트 케이스별 목적

분류는 네 가지로 나눴다. 기존은 원래 있던 동작이 그대로인지, 확장은 새 기능이 동작하는지, 경계는 잘못된 입력이나 판 끝, 한도 같은 가장자리 경우를, 설계는 구조를 바꿔도 결과가 같은지 또는 불변성, 공유, 스레드 같은 설계상의 성질을 본다. 목적 칸에는 그 테스트를 왜 만들었는지, 어떤 잘못을 잡으려는지를 적었다.

DirectionTest (5개)

원본 클래스 Direction을 대상으로 빌드와 테스트 환경이 돌아가는지 처음 확인할 때 만든 테스트다. Direction은 화면과 무관해 바로 시험할 수 있었다.

clear하면_NONE으로_돌아간다기존모든 비트가 켜진 ALL에서 clear가 비트를 남김없이 지우는지 본다.

(3) 예측 모델과 실제 판의 비교: GenerationMatchesBoardTest

예측에 쓰는 Generation은 화면의 판과 다른 코드로 세대를 진행한다. 이 테스트는 판 끝에 부딪히는 Glider를 양쪽에서 260세대 돌리며 매 세대 좌표를 비교하고 마지막 모양이 더는 변하지 않는지도 본다. 비교를 맡는 도우미 메서드를 함께 실었다.

@Test
void Glider가_판_끝에_부딪혀_멈출_때까지_실제_판과_같다() {
    // 왼쪽 위에서 오른쪽 아래로 가는 Glider. 판 끝에 닿으면 4칸으로 멈춘다.
    Set<Point> glider = Set.of(new Point(1, 0), new Point(2, 1),
                               new Point(0, 2), new Point(1, 2), new Point(2, 2));

    Generation last = assertSameAsBoard(glider, new ConwayRule(), 260);

    assertEquals(4, last.liveCells().size());
    assertEquals(last, last.next(new ConwayRule()));      // 더는 변하지 않는다
}

private Generation assertSameAsBoard(Set<Point> start, Rule rule, int generations) {
    RuleHolder holder = new RuleHolder();
    holder.change(rule);
    Cell board = newBoard(holder);
    for (Point cell : start) {
        click(board, cell.x, cell.y);
    }
    Generation generation = new Generation(start, WIDTH);

    for (int n = 0; n < generations; n++) {
        assertEquals(liveCells(board), generation.liveCells(), n + "세대에서 달라졌다");
        step(board);
        generation = generation.next(rule);
    }
    assertEquals(liveCells(board), generation.liveCells(), generations + "세대에서 달라졌다");
    return generation;
}

6-4. 모델을 UI와 분리해 테스트한 것

113개 테스트 중 Universe, Clock, Swing 컴포넌트를 쓰는 것은 하나도 없다. Universe는 창과 메뉴를 만들어야 생기기 때문에, 판이 필요한 테스트는 Universe와 같은 구조의 Neighborhood 판을 직접 만들고 userClicked와 figureNextState, transition을 불러 클릭과 세대 진행을 흉내 낸다.

Generation과 EndingPredictor는 살아 있는 칸의 좌표 집합과 Rule만 받으므로 판도 화면도 없이 시험했다. PredictionWorker는 생성자로 계산 함수와 결과를 받을 함수를 받기 때문에, 테스트에서는 진짜 예측기 대신 CountDownLatch로 끝나는 시점을 정한 가짜 계산을 넣었다. StatusLine은 Swing을 쓰지 않고 글자와 색(java.awt.Color)만 만들며 그것을 실제 화면에 올리는 일은 Universe가 한다. 그래서 옛 예측을 버리는 규칙, 남은 세대 계산, 자동 정지 판단(isFinished())을 창 없이 확인할 수 있었다.

반대로 Universe에 남은 연결 코드, 곧 잠금, 메뉴 처리, isFinished()를 보고 Clock을 멈추는 부분은 JUnit으로 확인하지 않았다.

이 연결 부분은 두 가지로 대신 확인했다. 첫째, 창을 화면에 띄우지 않고 같은 프로그램을 돌려 클릭·세대 진행·메뉴를 코드로 흉내 내고 창 아래 글자를 읽었다(docs/experiments/StatusCheck.java, AutoStop.java). 둘째, 실제 창에서 남은 세대 수가 줄어드는 것, 자동 정지, B0/S에서 판 전체가 깜빡이는 것을 눈으로 확인했고 마지막에는 같은 이벤트를 코드로 보내 단계마다 창 그림을 떠서 확인했다(5-5절). 파일 선택 창이 뜨는 Load와 Store는 이렇게 확인하기 어려워 시연 영상으로 보인다.
